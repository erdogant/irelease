CLI Reference
==============

Overview
--------

The command‑line interface (CLI) for the Interactive Release Tool is a thin, automatically generated layer that translates user intent expressed on the shell into concrete calls to the core release logic housed in :mod:`irelease`. Rather than hand‑coding argument parsers and configuration loaders, the project leverages **Clizard** – a declarative framework that scaffolds an interactive CLI from a minimal specification. This approach guarantees that any change to the underlying API is reflected in the user interface without manual edits, thereby reducing maintenance overhead and ensuring consistency across all release tools.

At its core the wrapper exposes two public entry points: :func:`build_cli` and :func:`main`. The former constructs a fully configured :class:`~clizard.GenericCLI` instance, while the latter is the console‑script hook that simply invokes the CLI’s run loop. Together they provide a seamless experience for both scripted automation and interactive use cases such as prompting for missing values or confirming destructive actions.

The design of this module is intentionally minimalistic; it delegates all heavy lifting to **Clizard** so that developers can focus on the release workflow itself. By keeping the wrapper autogenerated, any future signature changes in :mod:`irelease` automatically propagate to the CLI without requiring manual edits. This guarantees that the command‑line experience remains in lockstep with the core logic and eliminates a common source of bugs where documentation or help text becomes stale.

Interactive CLI Wrapper for irelease
------------------------------------

The wrapper is generated automatically by **Clizard** from a small declarative specification. The code you see in :mod:`clizard_main` is therefore not hand‑written but synthesized to match the current ``irelease`` API. This design choice eliminates duplication of argument handling logic across multiple tools and guarantees that future changes to the core release functions propagate automatically to the CLI.

The wrapper consists of four key components:

* **:class:`~clizard.GenericCLI`** – a lightweight abstraction that knows how to register sub‑commands, display help text, and validate input types. It is the foundation upon which **Clizard** builds every command line interface in this project.
* **:func:`load_clizard_file`** – reads a ``.clizard`` configuration file from either a user‑supplied path or the default location (``~/.clizard``). This file can override defaults such as the executable name, global flags, and even sub‑command signatures.
* **:func:`build_cli`** – creates an instance of :class:`~clizard.GenericCLI`, applies configuration defaults from the ``.clizard`` file, registers the ``/run`` command (which forwards directly to :func:`irelease.run`), and returns the fully configured CLI object. It accepts a *path* parameter of type Path‑like that is optional.
* **:func:`main`** – the entry point used by setuptools’ console scripts; it simply builds the CLI and executes it via ``cli.run()``.

Why this design? By delegating all command‑line parsing to a generated wrapper, developers avoid duplicating argument handling code across multiple tools. The wrapper also guarantees that any future changes to the core API automatically propagate to the CLI without manual intervention—just regenerate with **Clizard**. Moreover, because the CLI is built on top of :class:`~clizard.GenericCLI`, it inherits robust features such as automatic help generation, type checking, and support for interactive prompts when needed.

^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Example usage
-------------

.. code-block:: python

    from clizard_main import main

    # Invoke the CLI directly (this would normally be called by setuptools)
    if __name__ == "__main__":
        main()

Design Decisions and Trade‑offs
-------------------------------

* **Auto‑generation** – The wrapper is regenerated whenever the core API changes. This eliminates manual edits but requires developers to run *Clizard* after any signature change.
* **Fallback mechanism** – If a local ``clizard`` package is unavailable, the wrapper falls back to ``genericli`` for standalone scripts. This ensures that the CLI can still be executed in minimal environments.
* **Configuration precedence** – Settings from a user‑supplied ``.clizard`` file override baked defaults. When no configuration file exists, the wrapper uses :data:`_DEFAULT_SETTINGS` defined at generation time. This design balances flexibility with sensible fallbacks.
* **Parameter validation** – All arguments are validated against types and choices specified in the ``.clizard`` file. This reduces runtime errors and provides immediate feedback to users.

Verbosity parameter
-------------------

The global ``verbosity`` option is documented in :data:`_DEFAULT_ARG_META`. It controls the logging verbosity level of the CLI:

* **Valid values** – ``0``, ``1``, ``2``, ``3``, ``4``, ``5`` (integer)
* **Default value** – ``2`` as defined in :data:`_DEFAULT_SETTINGS`
* **Description** – “Logging verbosity level”

This information is now explicitly reflected in the documentation to avoid confusion for users.
