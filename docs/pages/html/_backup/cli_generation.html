cli_generation

Overview of the CLI Generation Process

The pyrelease-cli command line interface is not hand‑crafted; it is produced automatically by the clizard framework. The generator consumes the core release logic defined in irelease.py and wraps it inside a GenericCLI object. This design keeps the public API minimal while still exposing every feature of the underlying workflow, because all command‑line options are derived from the release script itself rather than being hard coded in separate modules.

When a user invokes the entry point – for example pyrelease-cli run – the generated script first resolves any configuration files present in the current working directory. Optional .clizard files allow users to override defaults such as the package name or username, and they also provide authentication details required by tools like Twine. This approach gives power to advanced users without burdening newcomers with a long list of flags.

Once configuration is resolved, build_cli() constructs a GenericCLI instance. The instance is configured with sensible defaults for all options that are not explicitly supplied in the config file: the GitHub username, the target package name, whether to clean the build directory, whether to install the built wheel locally, whether to invoke Twine for uploading, and the verbosity level of output. These defaults ensure that a new user can simply run pyrelease-cli run without having to remember any flags. The CLI registers a single high‑level command, /run, which forwards all parsed arguments directly to irelease.main(). This forwarding is performed either by passing the raw sys.argv list or by converting the parsed options into keyword arguments; both paths are supported for maximum flexibility.

The final step in the generation process is to return the fully configured CLI object. The top‑level main() function then calls this builder, obtains the GenericCLI, and immediately invokes its run() method. From that point on, the user can either supply command line arguments or answer interactive prompts. Because the CLI logic lives in a separate module generated by clizard, any changes to the release script are automatically reflected without manual edits. This separation of concerns keeps maintenance low and guarantees that the public interface remains stable even as the underlying algorithm evolves.

Key Functions

build_cli()

Constructs and configures the command‑line interface used by pyrelease-cli. The function performs three distinct steps:

  1. Load Configuration – Attempts to read a .clizard file in the current working directory. If present, values from this file override any hard‑coded defaults.

  2. Set Defaults – For every option that is not supplied by configuration or command line arguments, a default value is applied. These defaults are chosen to provide an out‑of‑the‑box experience for typical release scenarios.

  3. Register Commands – A single /run command is added to the GenericCLI. This command forwards all parsed options to irelease.main(), ensuring that the full release workflow is accessible from the CLI.

The function returns a fully configured GenericCLI instance ready for execution.

Using build_cli() directly
from clizard_main import build_cli

cli = build_cli()
# At this point, `cli` can be inspected or modified before running.
cli.run()
main()

Entry point for the generated CLI. It simply calls build_cli() to obtain a configured GenericCLI instance and then executes it by invoking its run() method. This thin wrapper keeps the public API small while delegating all heavy lifting to clizard.

Important Notes

  • The CLI is built by clizard_main.build_cli which registers a /run command that forwards arguments to irelease.main.

  • Configuration overrides can be supplied via a .clizard file in the current working directory.

  • Defaults are applied when configuration values are absent, ensuring a smooth out‑of‑the‑box experience.
